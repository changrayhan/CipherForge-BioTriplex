# 04 · 备用方案与降级预案

> 目标：**任何单点故障都不导致现场演示中断。** 本文档同时面向平台使用者与服务器开发。

## 1. 三级兜底体系

| 级别 | 场景 | 机制 | 对评委的呈现 |
| --- | --- | --- | --- |
| L1 | 微调耗时超预期（真实模式） | **预微调检查点切换**：跳过训练，加载事先微调好的 LoRA，直接进评测 | 真实通信不中断，仅训练段被替换 |
| L2 | 服务器/网络整体不可用 | **本地演示模式**：平台内置三方模拟器跑通完整流程 | 流程、界面、数据流完全一致 |
| L3 | 平台进程本身故障 | **预录视频 + 日志快照** | 播放彩排录像，展示历史日志 |

## 2. L1：预微调检查点切换（训练跳过）

### 2.1 触发

主持人连击页面左上角印章 5 次 → 工程控制台 → 「跳过训练 · 加载预微调检查点」。
（也可 `POST /api/fallback/pretrained {"reason":"..."}` 触发。）

### 2.2 信令流程

```
平台                     S 节点                M 节点                U 节点
 │ POST /v1/fallback/pretrained {checkpoint_id, trace_id}
 │───────────────────────▶│                     │                    │
 │  S：记录任务状态切换、登记检查点为评测基准       │                    │
 │ POST /v1/fallback/pretrained                                      │
 │──────────────────────────────────────────────▶│                    │
 │                        M：加载 LoRA 检查点 θ*（替换/旁路当前 θ）    │
 │ POST /v1/fallback/pretrained                                       │
 │────────────────────────────────────────────────────────────────────▶│
 │                          U：记录会话切换（数据侧无需变更）            │
 │ 平台进入 EVAL 阶段，总控台标注「已启用预微调检查点」
```

### 2.3 服务器开发约定

1. **检查点准备**：彩排前用真实管线在 ClinVar 上微调得到 LoRA 检查点，三方统一命名
   `checkpoint_id`（默认 `clinvar-tinyllama-lora-r8-20260815`，以 `platform.config.json` 为准）。
2. **M 节点**必须实现加载逻辑：将 `θ*` 加载为当前 LoRA 参数，返回 `{ok:true, loaded:true, load_ms}`。
3. **S 节点**将后续 `/v1/eval/run` 的 "after" 侧绑定到 `θ*` 对应的模型产物。
4. **U 节点**幂等返回即可。
5. 任一节点加载失败：平台标红但继续；主持人可改走 L2。

### 2.4 现场话术

> 「真实微调单步约 12 秒、完整流程需要数分钟。为节约时间，我们切换到彩排时由同一管线产出的检查点，后续评测与通信仍是实时真实的。」

## 3. L2：本地演示模式

- 切换：工程抽屉 → 「本地演示模式」。切换时进行中的会话会自动中止。
- 该模式下平台内置 U/M/S 模拟器，事件流、阶段、拓扑动画与真实模式**完全一致**（数值为按演示配置合成的拟真值）。
- 界面上模式徽标会显示「本地演示模式」——切换前请确认评委视角不聚焦顶栏，或由主持人口径管理。
- 另有「自动推进」开关：开启后无需逐方点击，全流程自动演示（约 90 秒）。

## 4. L3：预录视频与日志快照

- 彩排时完整录制三方 + 总控屏视频，存放 `data/replay/`（自行拷贝）。
- 平台历史日志在 `logs/platform-*.log`；事件流含全部 trace，可作为证据展示。
- 建议同时导出评测台各测试结果的截图/JSON（`GET /api/eval/tests` 返回已运行结果）。

## 5. 故障决策树

```
现场开始
  ├─ 三节点探活全绿？ ──否──▶ 重试一次 → 仍失败 → L2 本地演示模式
  └─ 是
     ├─ 训练阶段耗时 > 预期阈值？ ──是──▶ L1 预微调检查点
     ├─ 某动作失败？ ──▶ 该方页面重试一次 → 仍失败 → L1（若在训练段）或 L2
     └─ 平台卡死？ ──▶ 重启 node server/index.js（状态重置）→ L2/L3
```

## 6. RMS-PIR 备用 PIR 模式（2026-08-19 起提供；v2 职责划分）

### 6.1 是什么

RMS-PIR 是 Ren-Mughees-Sun 2024（ACM CCS'24）论文 *Simple and Practical
Amortized Sublinear Private Information Retrieval using Dummy Subsets* 的
**两服务器变体**，在本仓库中作为 `pir_mode: "rms"` 备用方案实现：

- **离线阶段**：U 从私有种子推导 hint 子集（n=160 个分区 × 200 行，M=λ·n 个
  hints），**由 U 本地计算**每个 hint 的 parity（U 先一次性下载 S 的密文库副本
  到 `party_u/db/`，用本地 BFV worker 做密文和），存到
  `party_u/data/rms_hints/`；对已知标签 {空格, Yes, No} 确定性**补足** hint 池
  至 `rms_min_coverage`，保证批内不会断供。
- **在线查询**：对标签 y 取一个包含 y 的 hint，构造真实子集（hint 子集去掉 y）
  与假子集（覆盖其余分区），随机置换后发给 S；S 返回两个子集的 parity
  （**明文聚合**：逐行 round(V·scale) 整数求和后一次 BFV 加密，与密文和位级一致）；
  U 用 `hint_parity ⊖ 真实子集 parity` 恢复 Enc(-V_y)，加 PRG 掩码后发给 M
  —— 与块 PIR 相同的线上协议格式。
- **hint 补充**：每查询消耗 1 个 hint，S 返回下一个 hint ID 的两个半区 parity，
  **改为 U 本地计算**两个半区 parity，U 取不含 y 分区的半区 + Enc(-V_y)
  组成新 hint（分布与消耗的相同）；S 全程看不到 hint 子集与半区。

> **v1 → v2 的关键差异**：v1 中 S 同时担任“hint 构建者”与“在线应答者”，可把
> 查询子集匹配回已知 hint 子集；v2 把 offline 角色移到 U（持密文库副本），
> S 只做在线应答 → 论文的多查询隐私证明（Lemma 2 + §3.5）在单 S 部署下成立。

### 6.2 何时切换

1. 现场/评审要求“标准（有状态）PIR 多查询隐私”而非块 PIR 的统计抗性；
2. 具备**两个持库、非合谋**的服务器部署（offline server 建 hints、online server
   应答），此时 RMS-PIR 的单查询隐私是信息论不可区分的（论文 Lemma 2）；
3. 愿意承担离线成本：λ=16 时约 2600 个 hint ≈ 335 MB 下载 + S 端 ~60 s 计算
   （实测 2603 hints / 63 s），客户端存储随 λ 线性增长。

### 6.3 切换方式与参数

```bash
python coordinator/main.py --config coordinator/three_party_config_rms.json \
  --max_train_steps 625 --batch_size 16 --log_freq 10
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `pir_mode` | `block` | `rms` 启用备用模式 |
| `rms_partition_size` | 200 | 分区行数（n=160 个分区） |
| `rms_lam` | 16 | 初始 hint 池倍数（M=λ·n） |
| `rms_min_coverage` | 20 | 每个已知标签的最少 hint 数（确定性补足） |
| `rms_offline_chunk` | 64 | 离线 parity 请求的分块大小 |

### 6.4 安全边界（必须如实告知）

- **v2 已消除“S 关联 hint”风险**：S 只应答在线子集，从不接触 hint 子集与
  补充半区；单查询与多查询隐私均按论文成立。
- **新增的部署事实**：U 持有密文库副本（4.2GB，Enc(-V) 且 pk_M 加密，U 无 sk
  不可解密；V 本身是公开 lm_head 权重，不构成新机密泄露）。需要向评审/使用者
  说明“密文库同时存在于 U 的加密副本与 S 的原始库”，以及一次性的 4.2GB 下载。
- 块 PIR v2（默认）不要求 U 持库，但有多查询频率统计泄露（已压低至随机水平，
  见 `块PIR与S3PIR与RMS-PIR方案对比分析.md`）——两种模式按部署条件二选一。

### 6.5 验证结论（2026-08-19）

- 真实 SEAL 往返（v2）：`scripts/rms_roundtrip_verify.py`，36 次查询（含补充后
  hint 的二次查询；hint 用 U 侧密文和、在线子集用 S 侧明文聚合+加密），
  解密误差 **0.000000**（阈值 0.01）；
- 三进程冒烟（v2）：12 步 × batch=4，RMS parity / share / grad_reconstruct
  全 ok，梯度真实增长（g_absmax 1.97→4.56），稳态步时 ~1.0-2.5 s；
- v2 离线实测：密文库下载 89.9 s（4.20 GB，32MB 分块）；U 本地构建
  2599 hints（含 39 个补足）88.3 s；
- 隐私验证：S 日志只有每步 1 次的在线 `rms_parity`，**无任何 hint/半区请求**。
