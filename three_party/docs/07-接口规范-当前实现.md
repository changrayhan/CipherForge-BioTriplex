# 01 · 接口规范（当前后端实现）——面向前端 / AI 助手

> **目标读者**：需要为当前后端实现前端、或需要接入联调的 AI 助手与开发者。
> **后端位置**：远程服务器 `three_party/`（U/M/S 节点 + 演枢台平台）。
> **更新日期**：2026-08-21
> **协议版本**：`1.0`
> **对照文档**：`00-服务器开发交付包说明.md`（上传文档）；本文第 8、9 章说明当前实现与它的关系及差异。

---

## 0. 快速结论（先读）

1. 前端**只需要对接演枢台平台（`http://<host>:8600`）**的 `/api/*` 接口与 SSE 事件流；节点接口由平台代调，前端不直接访问 U/M/S。
2. 平台提供：节点探活、会话发起（INIT 编排）、L1 兜底（加载预微调检查点）、评测（acc/auprc/macro_f1 + 预设回放）、进度推送接收、SSE 事件流、状态查询/复位。
3. 三个节点统一实现 `GET /v1/hello`、`POST /v1/action`、`POST /v1/fallback/pretrained`、`POST /v1/eval/run`，全部为 HTTP/JSON，统一信封。
4. 与上传文档的主要差异（详见第 9 章）：BFV `plain_modulus` 与文档不一致、演示参数 batch/lr 不同、PIR 方案为 RMS-PIR v2/Block-PIR、U 节点 HTTP 动作只有 `pir_prg_setup`（其余 U 逻辑在 coordinator 进程内）、平台目前只编排 INIT 阶段（FORWARD→EVAL 由 coordinator 驱动）。

## 1. 架构与部署拓扑

```
浏览器/前端（演示笔记本）
        │  HTTP + SSE
        ▼
演枢台平台  :8600   (platform/server/index.js, Node 22, 零依赖)
        │  HTTP/JSON（平台代调）
   ┌────┼────┐
   ▼    ▼    ▼
  U节点  M节点  S节点
 :9001  :9002  :9003
(party_u (party_m (party_s
 main_u)  main_m)  main_s)
```

| 组件 | 端口 | 实现文件 | 说明 |
|---|---|---|---|
| 演枢台平台 | 8600 | `platform/server/index.js` + `platform/web/index.html` | 前端唯一入口；状态机 + SSE + 编排 |
| U 节点 | 9001 | `party_u/main_u.py`（框架 `shared/node_server.py`） | 数据方；HTTP 动作仅 `pir_prg_setup` |
| M 节点 | 9002 | `party_m/main_m.py` | 模型方；BFV 密钥、前向、梯度重建、LoRA 更新、检查点 |
| S 节点 | 9003 | `party_s/main_s.py` | 服务方；密文库、输出头、PIR 响应、份额、评测 |
| coordinator | 由菜单启动 | `coordinator/main.py` | 真实训练编排器；内嵌 U 方密码学逻辑，通过 HTTP 驱动 M/S |

平台配置：`platform/config/platform.config.json`（节点地址、超时、兜底检查点 ID、脱敏字段）。

## 2. 节点接口（U/M/S，协议 v1.0）

### 2.1 统一约定

- 全部请求/响应 `Content-Type: application/json; charset=utf-8`。
- 成功信封：`{ "ok": true, "events": [...], "metrics": {...}, "result": {...} }`
- 失败信封：`{ "ok": false, "error": { "code": 400, "message": "人类可读错误", "retryable": true|false } }`
- 幂等：`/v1/action` 按 `trace_id + stage + step + action` 缓存，重试返回轻量标记 `{ok:true, cached:true}`；数据返回型动作（`trunk_forward/val_forward/head_forward/fetch_rows/share_compute/rms_parity/db_download/val/gather_checkpoint`）不缓存。
- 脱敏：节点侧自动把事件/结果中以下字段替换为 `***`：`raw_text, label, sk_M, prg_seed, mask_vector, head_row, weights`（前端不要依赖这些字段，也不要主动上报）。

### 2.2 GET /v1/hello —— 握手与能力协商

请求：无参数。

响应（实测）：
```json
{
  "ok": true,
  "node_id": "srv-u-01",
  "role": "U",
  "protocol_version": "1.0",
  "capabilities": ["action", "fallback", "eval"],
  "assets": ["ClinVar 标注数据（仅本节点）", "embed_tokens + 底部 Decoder", "PIR 客户端（real+dummy 查询块）", "PRG 种子 σ（与 S 共享）"],
  "status": "idle"
}
```

| 字段 | 说明 |
|---|---|
| `role` | `U` / `M` / `S` |
| `protocol_version` | 当前恒为 `1.0` |
| `capabilities` | 三方均为 `["action","fallback","eval"]`（已与实现一致） |
| `assets` | 资产清单，平台直接展示 |
| `status` | `idle` / `busy` / `error` |

### 2.3 POST /v1/action —— 执行协议动作

请求：
```json
{
  "protocol_version": "1.0",
  "trace_id": "task_20260821000000_ab12",
  "stage": "INIT",
  "step": 0,
  "action": "bfv_keygen",
  "params": { "poly_degree": 4096, "plain_bits": 30, "scale": 10000 }
}
```

| 字段 | 说明 |
|---|---|
| `trace_id` | 必填；缺失返回 `{ok:false, error:{code:400, retryable:true}}` |
| `stage` | `INIT/DATA/FORWARD/BACKWARD/RECONSTRUCT/UPDATE/EVAL` |
| `step` | 训练步序号（非训练阶段为 0） |
| `action` | 见下方动作矩阵；未实现返回 `{ok:false, error:{code:501, retryable:false}}` |
| `params` | 动作参数；节点忽略不认识的键 |

响应：
```json
{
  "ok": true,
  "events": [ { "type": "crypto", "payload": { "msg": "BFV.KeyGen 完成", "poly_degree": 4096 } } ],
  "metrics": { "comm": [ { "edge": "M->U", "bytes": 32768 } ], "loss": 1.9326, "grad_error": 2.1e-8, "step_ms": 12400 },
  "result": { "pk_pem_b64": "...", "pk_sha256": "0x..." }
}
```

**动作矩阵（当前实现）**

| 执行方 | action | 语义 |
|---|---|---|
| M | `bfv_keygen` | BFV 密钥对生成/缓存，返回 `pk_pem_b64` |
| M | `init_runtime` | 加载模型 + PartyM + 加密 worker 池（params 为完整 worker_config） |
| M | `trunk_forward` | 顶部 Decoder + LoRA 前向，返回 `H_M` |
| M | `val_forward` | 验证模式前向 |
| M | `grad_reconstruct` | 接收密文/份额，准备梯度重建 |
| M | `debug_decrypt` | 调试解密 |
| M | `lora_update` | 梯度重建 + LoRA/AdamW 更新，返回 `loss/g_absmax/...` |
| M | `gather_checkpoint` | 收集 M 侧 LoRA/优化器状态 |
| M | `load_checkpoint` | 从参数加载 LoRA 状态（coordinator 用） |
| M | `shutdown` | 关闭 worker 池 |
| S | `init_runtime` | 保存 worker_config |
| S | `build_enc_db` | 构建/缓存 BFV 密文库（无 worker_config 时用参数/默认值自举） |
| S | `pir_prg_setup` | 登记 PRG 种子、初始化 PartyS + worker 池 |
| S | `head_forward` | `z=H_M·Wᵀ`，缓存 H_M，返回 `monitor_p_yes` |
| S | `fetch_rows` | 块 PIR 行取回，返回 `rows` |
| S | `share_compute` | 输出头份额计算，返回 `s_shares_b64` |
| S | `rms_parity` | RMS-PIR 在线 parity（明文聚合 + 一次 BFV 加密） |
| S | `db_download` | 向 U 流式下发密文库副本（RMS-PIR v2） |
| S | `val` | 验证前向（full logits） |
| S | `shutdown` | 关闭 worker 池 |
| U | `pir_prg_setup` | 登记 PRG 种子（幂等确认；真实 U 侧密码学逻辑在 coordinator 内） |

> 注意：文档矩阵中 U 的 `load_dataset / local_embed / pir_query_mask` 未暴露为 U 节点 HTTP 动作（见第 9 章差异 #4）。

**RMS-PIR v2 在线流程（coordinator 内驱动）**：
1. U 侧（coordinator 内嵌 PartyU + CryptoUWorker 池）本地维护 RMS hint 池（`rms_hints/hint_*.ct`，行集由 `rms_seed` 确定性生成）；每 token 弹出一个包含标签 y 的 hint；
2. `build_query` 生成 real（hint 行集 − y）与 dummy（其余分区各 1 随机行）两个 80 行子集，按 `perm` 打乱顺序通过 S 的 `rms_parity` 取回两条 parity；`perm==0` 取第 1 条、`perm==1` 取第 2 条作为 q_parity；
3. U 本地求 `recovered = hint_parity − q_parity = Enc(−V_y)`，加 PRG 掩码 r_t 后发 M；
4. 补货：以 `picked_half + [y]` 的本地新鲜 parity 写回 hint 池（`store.add_replenished`）。

> 2026-08-21 修复：`build_query` 返回约定为 `(first, second, perm)`（`perm==1` 时 first=dummy），调用方此前双重交换导致 q_parity 取到 dummy 子集（RMS 不学习根因），现已按 `row_lists=[first, second]` 正确接线。RMS seed 可用 `CF_RMS_SEED_HEX` 固定，并写入 `<run>/logs/rms_seed.txt`。

### 2.4 POST /v1/fallback/pretrained —— L1 兜底（加载预微调检查点）

请求：
```json
{ "protocol_version": "1.0", "trace_id": "task_...", "checkpoint_id": "clinvar-tinyllama-lora-r8-20260815" }
```

响应（三方一致）：
```json
{ "ok": true, "checkpoint": "clinvar-tinyllama-lora-r8-20260815", "loaded": true, "load_ms": 830 }
```

三方行为：
- **M**：真实加载 LoRA 检查点（默认 `party_m/checkpoints/best_checkpoint.pt`，可用 `--fallback_checkpoint` 指定）；`init_runtime` 之前调用则暂存、初始化后自动应用。检查点不存在时返回 `{ok:false, error:{code:500, retryable:false}}`。
- **S**：登记检查点，将后续 `/v1/eval/run` 的 after 侧绑定到该检查点（响应含 `checkpoint_id`）。
- **U**：幂等确认（数据侧无需变更）。

### 2.5 POST /v1/eval/run —— 评测接口

请求：
```json
{ "protocol_version": "1.0", "trace_id": "task_...", "test_id": "acc", "params": {} }
```

响应：
```json
{
  "ok": true,
  "result": {
    "status": "DONE",
    "metrics": [
      { "key": "before", "label": "微调前", "value": 49.98, "unit": "%" },
      { "key": "after",  "label": "微调后", "value": 70.81, "unit": "%" }
    ],
    "conclusion": "准确率（acc）：微调前 49.98% → 微调后 70.81%，提升 +20.8pp",
    "checkpoint_id": "clinvar-tinyllama-lora-r8-20260815"
  }
}
```

**test_id 清单**：
- 必测（真实数据，读取 `metrics_dir/clinvar_auprc.json` + 基线 fixture）：`acc`（`accuracy@0.5`）、`auprc`、`macro_f1`。
- 预设回放（`data/fixtures/eval-presets.json`，12 项）：`dli_baseline, dli_triadft, l1, l2, m1, m2, eia, grad_max_abs, grad_rel, step_time, comm, offline_db`。
- 未知 test_id：`{ok:false, error:{code:404, retryable:false}}`。

> before/after 数值来自**最近一次**评测产物（after = 最近训练的 adapter；before = 零样本基线 fixture）。用 3 步演示运行跑出的数值接近零样本水平，展示高指标需完整训练或使用预微调检查点（L1）。

## 3. 平台接口（演枢台 :8600）

平台是**前端唯一入口**，全部接口如下（均返回 JSON；`/api/stream` 除外）。

### 3.1 GET / —— 前端页面

返回 `platform/web/index.html`。页面已内置按钮：节点探活、开始会话、跳过训练（L1）、评测 acc/auprc/macro_f1；左上角"印章"连击 5 次触发 L1 兜底。

### 3.2 GET /api/state —— 平台状态

```json
{
  "mode": "remote",
  "nodes": { "U": { "status": "online", "info": { "role": "U", "proto": "1.0" } }, "M": {...}, "S": {...} },
  "session": { "trace_id": "task_...", "step": 0, "stage": "INIT" },
  "eval": { "test_id": "acc", "result": { "ok": true, "result": {...} } },
  "events": [ { "id": 1, "ts": 178724..., "type": "node", "party": null, "payload": {...} } ]
}
```

### 3.3 POST /api/nodes/probe —— 节点探活

平台依次调用三方 `/v1/hello`，更新 `state.nodes`，广播 `node` 事件；返回整个 state。前端可据此渲染徽标（online/error/offline）。

### 3.4 POST /api/session/start —— 发起会话（INIT 编排）

行为：
1. 生成 `trace_id = task_YYYYMMDDHHMMSS_xxxx`，`state.session = {trace_id, step:0, stage:"INIT"}`，广播 `session` 事件；
2. 从 `coordinator/three_party_config_rms.json` 读取 worker 参数（默认 vocab 32000 / hidden 2048 / poly_degree 4096 / plain_bits 30 / scale 10000 / lam 80）；
3. 生成 PRG 种子（`crypto.randomBytes(32)`）；
4. 顺序执行 INIT 动作并逐个广播 `action_done` / `action_failed`：
   - M `bfv_keygen`（携带 worker 参数）→ 取回 `pk_pem_b64`
   - S `build_enc_db`（携带 worker 参数 + `pk_pem_b64`）
   - S `pir_prg_setup`（`prg_seed_b64`）
   - U `pir_prg_setup`（同一 `prg_seed_b64`）

返回整个 state。**注意**：当前只编排 INIT；FORWARD/BACKWARD/RECONSTRUCT/UPDATE 等阶段由 coordinator 训练驱动，平台尚无阶段推进接口（差异 #5）。

### 3.5 POST /api/fallback/pretrained —— L1 兜底

请求体可选：`{ "checkpoint_id": "..." }`（缺省用平台配置的 `fallback.pretrained_checkpoint_id`，当前为 `clinvar-tinyllama-lora-r8-20260815`）。

按 **S → M → U** 顺序调用节点 `/v1/fallback/pretrained`，广播 `fallback_loaded` / `fallback_failed`，返回：
```json
{ "S": {"ok":true,"checkpoint":"...","loaded":true,"load_ms":0},
  "M": {"ok":true,"checkpoint":"...","loaded":true,"load_ms":45},
  "U": {"ok":true,"checkpoint":"...","loaded":true,"load_ms":0} }
```

### 3.6 POST /api/eval/run —— 评测

请求体：`{ "test_id": "acc" }`。平台调用 **S** 节点 `/v1/eval/run`，广播 `eval_done` / `eval_failed`，返回节点原始响应（`{ok, result:{status, metrics, conclusion, checkpoint_id?}}`）。

### 3.7 GET /api/eval/tests —— 评测项目清单

```json
{ "required": ["acc", "auprc", "macro_f1"], "tests": { "dli_baseline": {...}, ... } }
```
（来自 `data/fixtures/eval-presets.json`，共 12 个预设项。）

### 3.8 POST /api/ingest —— 节点进度推送（接收端）

请求体：`{ "party": "U", "type": "pir", "trace_id": "...", "payload": { "msg": "...", "edge": "U->S", "bytes": 145408 } }`。
平台将事件广播到 SSE（type 取 `body.type`，缺省 `ingest`）；返回 `{ok:true}`。**注意**：当前节点/coordinator 尚未主动调用此接口（差异 #6），前端可先按"预留"处理。

### 3.9 POST /api/reset —— 复位

清空 `session / eval / fallback / events`，广播 `state` 事件，返回 state。

### 3.10 GET /api/stream —— SSE 事件流

`text/event-stream`，连接即推送 `hello` 事件与最近 50 条历史事件。事件统一格式：
```json
{ "id": 12, "ts": 1787242650992, "type": "eval_done", "party": "S", "trace_id": "task_...", "payload": { "msg": "...", "result": {...} } }
```

事件类型：

| type | 触发场景 | payload 关键字段 |
|---|---|---|
| `hello` | SSE 连接 | `msg` |
| `node` | 探活 | `msg`, `nodes` |
| `session` | 会话发起 | `msg` |
| `action_done` / `action_failed` | INIT 编排每步 | `msg`, `code` |
| `fallback_loaded` / `fallback_failed` | L1 兜底 | `msg`, `checkpoint_id` |
| `eval_done` / `eval_failed` | 评测 | `msg`, `result` |
| `ingest` | `/api/ingest` 推送 | `msg` 等（透传） |
| `state` | 复位 | `msg` |

## 4. 事件类型与数据流（节点 events[] 常用 type）

| type | 语义 | 典型 payload 字段 |
|---|---|---|
| `message` | 跨方消息 | `edge`, `bytes`, `hash`, `msg` |
| `crypto` | 密码学操作 | `msg`, `poly_degree` |
| `pir` | PIR 查询/响应 | `edge`, `bytes`, `msg`, `query_id` |
| `compute` | 计算动作 | `msg` |
| `monitor` | 训练监控 | `msg`, `loss` |
| `task` | 任务状态 | `msg` |
| `data` | 数据传输 | `msg` |

`edge` 取值：`U->M, M->U, U->S, S->U, S->M, M->S`（前端拓扑动画按此渲染）。

---

## 5. 脱敏铁律（前端渲染注意事项）

- 禁止出现在任何上报/日志中的内容：原始文本、真实标签、`sk_M`、PRG 种子、掩码向量明文、输出头行向量明文、模型权重。
- 只允许：样本/查询/掩码的 ID 或哈希、密文哈希与尺寸、耗时、误差、统计指标。
- 平台二次脱敏：`security.hidden_fields` 命中即替换为 `***`（`platform.config.json`）。
- 前端若自行接节点日志/事件流，应同样遵守，不得展示疑似敏感字段。

## 9. 当前后端与上传文档的不一致之处（重点）

> 以下差异是**当前实现与 00 上传文档**的差异；多数属于"文档落后于实现/实现按用户要求保持不变"。

### #1 BFV 参数：`plain_modulus` 统一（2026-08-21 已修复）
- 文档：`poly_degree=4096, plain_modulus=536903681`
- 实际：`poly_degree=4096` 一致；SEAL 按 `plain_bits=30` 自动选模数，实测 `PlainModulus.Batching(4096,30) = 1073692673`。
- 2026-08-21 起，`shared/core/bfv_privselect_v2_adapter.get_plain_modulus()` 为统一入口，`coordinator/main.py`、`party_s/main_s.py`、`party_m.py` 梯度重建、`PRGShareProtocolBFV` 全部使用该真实模数（此前存在 `2^30` 与 `2^30+27` 两处记账值不一致的脆弱依赖，已消除）。
- 影响：前端无需感知；如需展示加密参数，请使用 1073692673。

### #2 演示训练参数不一致
- 批次大小：文档 4，实际默认 **16**（可用 `CF_BATCH_SIZE` 覆盖）。
- 学习率：文档 `1e-4`，实际 **`2e-4`**。
- 训练步数：文档 3，实际默认 **3 个 epoch（≈1875 步）**；用 `CF_MAX_STEPS=3` 可达成文档的 3 步演示。

### #3 PIR 方案描述不一致
- 文档：`两阶段 √N×√N`
- 实际：RMS-PIR v2（`rms_partition_size=200, rms_lam=16`，默认 RMS 变体）或 Block-PIR（`pir_block_size=64, pir_fake_ratio=0.25`）。

### #4 U 节点动作未全部暴露为 HTTP
- 文档矩阵：U 承担 `load_dataset / local_embed / pir_query_mask / pir_prg_setup`。
- 实际：U 节点 HTTP `/v1/action` 只有 `pir_prg_setup`（登记/确认）；其余 U 侧密码学与数据逻辑运行在 **coordinator 进程内**（`coordinator/main.py` 内嵌 PartyU）。前端若直接调 U 的其他动作会得到 501。

### #5 平台阶段编排不完整
- 文档：平台按阶段驱动 INIT→DATA→FORWARD→BACKWARD→RECONSTRUCT→UPDATE→EVAL。
- 实际：平台只编排 INIT 四个动作；训练循环（FORWARD→UPDATE）与评测由 coordinator 驱动，平台没有阶段推进/单步执行接口。

### #6 节点→平台进度推送未启用
- 文档：`POST {platform}/api/ingest`（可选但推荐）。
- 实际：平台接收端已实现，但节点/coordinator **尚未主动推送**进度事件。

### #7 预设回放数值为占位
- 文档列出的非必测 test_id（dli/l1/l2/m1/m2/eia/性能类）已全部可回放，但数值为拟真/占位值，标注"预设回放"。

### #8 eval/run 数值口径
- 文档示例 before=61.2 → after=88.5（完整训练水平）。
- 实际 before/after 来自最近一次评测产物：3 步演示运行 ≈ 零样本水平（acc≈50%、AUPRC≈47%）；完整训练或 L1 检查点可到 acc≈70.8%、AUPRC≈76.4%。

### #9 运行环境依赖
- 文档未提及 Node 版本；当前平台依赖 Node 22（已安装于 `/opt/node`，`node` 已在 PATH）。前端如需本地起平台，需 Node ≥ 18（使用 `fetch`/`AbortController`）。

## 11. BFV 密钥、密文库、hints 缓存位置与数据保存位置（交接）

### 11.1 加密产物（默认每次运行重新生成；`CF_CACHE_CRYPTO=1` 复用）

根目录：`<CF_CRYPTO_ROOT>`（默认 `/root/autodl-tmp/CipherForge-final-test/crypto`），按模式分子目录：`three-party-rms-pir/`、`three-party-block-pir/`。

| 路径（模式子目录内） | 内容 | 说明 |
|---|---|---|
| `m_keys/bfv_sk.bin` | M 方 BFV **私钥**（SEAL SecretKey 序列化，权限 600） | `bfv_keygen` 写入；解密验证/复现 hint 必须用它 |
| `m_keys/bfv_pk.bin` | M 方 BFV 公钥 | 分发给 U/S 加密 |
| `enc_db/bfv_ct_db_n32000_d2048_p4096.bin` | S 构建的 Enc(−V) 密文库（约 4.2 GB，32000 行 × 2048 维） | 80 字节头 + 每行 4 字节长度前缀 + SEAL Ciphertext 字节 |
| `enc_db/s3pir_hints/` | Block-PIR HintTable 缓存（`hint_table.json` 等） | S 侧 |
| `rms_db/bfv_ct_db_n32000_d2048_p4096.bin` | U 从 S 下载的本地密文库副本 | 与 `enc_db` 内容 sha256 一致（RMS-PIR v2） |
| `rms_hints/hint_*.ct` | RMS 初始 hint 池 + 训练中补货 hint 的 parity 密文 | 每 hint 一个文件，行集由 `rms_seed` 确定性生成 |

> 磁盘占用：每次三进程运行约 8–12 GB（enc_db 4.2 + rms_db 4.2 + hints 若干 + 密钥）。复用缓存的注意事项：`m_keys` 必须与 `enc_db/rms_db` 使用同一轮密钥；同目录内天然一致。

### 11.2 数据与运行产物保存位置

| 类别 | 位置 |
|---|---|
| 模型快照 | `/root/hf_cache/hub/models--TinyLlama--TinyLlama-1.1B-Chat-v1.0/snapshots/fe8a4ea1ffedaf415f4da2f062534de366a451e6/` |
| 数据集 | `three_party/party_u/data/qa/`（train/val/test.jsonl） |
| 运行产物 | `<CF_OUT_ROOT>/<tag>_<ts>/`（默认 `/root/CipherForge/final-test-data/`） |
| 三模式对比图 | `<CF_OUT_ROOT>/comparison_<ts>.png` |
| L1 兜底检查点 | `party_m/checkpoints/best_checkpoint.pt`（可 `--fallback_checkpoint` 覆盖） |
| 平台 | `platform/server/index.js`（:8600）、`platform/config/platform.config.json`、`demo/logs/` |
| 评测基线/预设 | `data/fixtures/clinvar-zeroshot-metrics.json`、`data/fixtures/eval-presets.json` |

### 11.3 RMS seed 与离线复现/验证

- coordinator 每次运行以 `os.urandom(32)` 生成 RMS seed（可用 `CF_RMS_SEED_HEX` 固定）；seed 写入 `<run>/logs/rms_seed.txt` 与 coordinator.log（`RMS seed (hex): ...`）。
- hint 池（2560 初始 + top-up + 训练补货）的行集全部由 seed 确定性生成；保留 seed + `m_keys/bfv_sk.bin` 即可离线复现并解密校验任意 hint 的 parity（对明文 V）。
