# 块 PIR、S3PIR、RMS-PIR 方案对比分析

> 版本：2026-08-19
> 适用范围：CipherForge 三进程（U/M/S）隐私保护微调中的“标签行私密取回”环节。
> 背景参数：TinyLlama-1.1B，词表 N=32000，hidden_dim=2048，BFV poly_degree=4096，
> 单行密文 ≈ 131 KB（`bfv_ct_db_n32000_d2048_p4096.bin`，4.198 GB / 32000 行）。

## 0. 三种方案在本项目里的角色

| 方案 | 角色 | 状态 |
|---|---|---|
| 块 PIR（Block PIR） | 当前默认的真 PIR 实现：真实行混入 dummy 行，S 返回整块，U 私有置换取行 | 已上线，本文档记录其改进版 |
| S3PIR | 论文 *Simple and Practical Amortized Sublinear Private Information Retrieval using Dummy Subsets*（Ren, Mughees & Sun, ACM CCS 2024，实现仓库 renling/S3PIR）的**正式方案**，即“带 dummy 子集的有状态亚线性 PIR” | 本仓库仅有 hint 骨架（`s3pir_hints.py`），**未参与运行时查询**；本文档按论文口径分析 |
| RMS-PIR | 同一论文的**两服务器变体**（offline server 建 hints / online server 应答），论文中以 “Our scheme / two-server scheme” 表述；本仓库按论文 §3 实现为三进程版的备用方案 | 备用方案，默认关闭（`pir_mode: "block"`） |

> 术语说明：论文中并没有单独叫 “RMS-PIR” 的方案，本文沿用项目内已建立的叫法，
> 指 Ren-Mughees-Sun 2024 的两服务器有状态 PIR（offline hints + 在线真/假子集应答）。

## 1. 机制速览

### 1.1 块 PIR（当前默认）

```text
U（持有标签 y）
   │ 构造查询块：真实行 y + (block_size-1) 个 dummy 行，随机置换
   │ 只发送“行索引集合”，不告诉 S 哪个是真实行
   ▼
S（持有密文库 Enc(-V)）
   │ 返回整块 block_size 行密文（mmap 按索引取行，零同态运算）
   ▼
U：按私有置换取回 Enc(-V_y)，同态加 PRG 掩码 r_t → Enc(-V_y + r_t)
   ▼
M：解密 + s_share(= a_t - r_t) → 梯度 (a_t - V_y)·scale
```

特点：**无离线阶段、无 hints、客户端零存储**；代价是每查询通信 =
block_size × 131 KB，且 S 端计算是纯 IO（mmap 切片），不做同态运算。

### 1.2 S3PIR / RMS-PIR（论文方案）

论文的核心结构（§3）：

1. **分区**：数据库 N 行分成 n 个大小相同的分区（论文取 n≈√N，每区 √N 行）。
   本项目实例化：n=160 个分区 × 200 行 = 32000 行。
2. **hint 构造（离线）**：每个 hint 均匀随机选 n/2+1 个分区，每个选中分区按 PRF
   偏移取一行，另加一个“额外索引” e_j（来自未选中分区）。hint = 该子集的
   **奇偶校验（parity，即密文和）**。客户端存 M = λ·n 个 hints。
3. **在线查询**：对目标 y，找到包含 y 的 hint，构造两个子集并随机置换：
   - 真实子集：hint 子集去掉 y（覆盖 n/2 个分区）；
   - 假子集：覆盖其余 n/2 个分区（每区一个随机行）。
   两个子集**并起来恰好覆盖全部 n 个分区**，且置换顺序随机。
4. **应答**：S 返回两个子集的 parity（各 n/2 次密文加法），共 2 个密文；
   U 用 `存储的 hint parity ⊖ 真实子集 parity` 恢复 Enc(-V_y)。
5. **hint 补充**：每个查询消耗 1 个 hint，立即由 offline server 用“两个半区 parity”
   补充一个新 hint（新 hint 以 y 为额外索引，分布与消耗的 hint 相同）。

**两服务器与单服务器变体的区别**（论文 §3.3/§3.4）：

| | 两服务器（RMS-PIR，本仓库备用实现） | 单服务器（S3PIR 正式方案） |
|---|---|---|
| offline 阶段 | offline server 用客户端 PRF 密钥构造 hints | 客户端流式下载全库、本地构造 hints |
| hint 补充 | 每查询由 offline server 在线补充（发两个半区 parity） | 预先存 λ√N/2 对 backup hints，用完再跑 offline |
| 客户端能力要求 | 无（可不解密） | **客户端必须能处理明文数据库**（本项目 U 不可解密，不满足） |
| 服务器要求 | 两个非合谋、都持库的服务器 | 单服务器即可 |

## 2. 性能与效率对比

> 以下“本项目实测”数字来自：
> - 块 PIR：三进程全量训练日志（2026-08-19，真实 SEAL + 真实密文库）与改进版冒烟测试；
> - RMS-PIR：本仓库备用实现的往返/冒烟测试（真实 SEAL）；
> - 论文数字：论文 §4.3 的 AWS m5.8xlarge（3.1 GHz Xeon，单线程）实测，数据库为
>   2^28 × 32 B = 8 GB（与我们的 32000 × 131 KB ≈ 4.2 GB 同量级）。

### 2.1 单查询成本

| 指标 | 块 PIR（block=8，旧） | 块 PIR（block=64 + 假查询，新） | RMS-PIR（本仓库参数） | 论文两服务器 | 论文单服务器（S3PIR） |
|---|---:|---:|---:|---:|---:|
| 离线阶段 | 无 | 无 | M=λ·n hints（λ=80 时 12800 个 ≈1.68 GB） | 一次建 12800 hints | 流式下载全库 |
| 离线计算 | 0 | 0 | ~1 M 次密文加法（可并行） | O(λN) | O(λN) |
| 客户端存储 | 0 | 0 | ≈1.68 GB（λ=80） | O(λ√N) | O(λ√N) |
| 请求大小 | 64 B（索引） | 512 B（索引） | ≈180 B（160 位 bit-vector + 160 个偏移） | √N/2+1 个词 | 同左 |
| 响应大小 | 8×131 KB≈1.05 MB | 64×131 KB≈8.4 MB | 2×131 KB≈262 KB | 2×条目 | 2×条目 |
| S 端每查询计算 | mmap 取 8 行 | mmap 取 64 行 | 160 次行读取 + 159 次密文加（两子集合计）+ 补充 160 次 | O(√N) 加法 | O(√N) 加法 |
| 论文实测（8 GB 库） | — | — | — | 34 KB 通信、2.7 ms | 46.9 KB 摊销、4.5 ms |

### 2.2 每训练步（32 个监督 token）成本

| 指标 | 块 PIR block=8 | 块 PIR block=64+20% 假块 | RMS-PIR |
|---|---:|---:|---:|
| S→U 密文传输 | 32×8×131 KB ≈ 34 MB | 名义 336 MB，**按唯一行去重后 ~0.4-9 MB**（dummy 集中在标签域，每步唯一行仅 ~3-70） | 32×2×131 KB ≈ 8.4 MB（响应）+ 8.4 MB（补充） |
| 假查询开销 | 0 | +25% 请求/响应 | 无（假子集已内建于每次查询） |
| S 端同态运算 | 0 | 0 | ~320×32 ≈ 10k 次密文加载/加法 |
| U 端运算 | 8 行取 1 + 掩码 | 64 行取 1 + 掩码 | 查 hint（O(1)/hint）+ 1 次密文减 + 掩码 |

结论：

1. **块 PIR 的名义通信随块大小线性增长**（block=8→64 时每步从 ~34 MB 涨到
   名义 ~336 MB）；由于 v2 的 dummy 对齐集中在标签域，取行端按唯一索引去重后
   实际每步仅传 ~0.4-9 MB，瓶颈大幅缓解（实测 batch=4 稳态 ~0.4 s/步）。
2. **RMS-PIR 的在线通信最优**（每步 ~17 MB），但把成本转移到离线阶段
   （1.68 GB 客户端存储 + 百万级密文加法）与每查询 O(√N) 的 S 端同态加法。
3. **S3PIR 正式单服务器方案需要客户端流式下载整个明文数据库**，与本项目
   “U 不可解密、S 是唯一持库方”的约束直接冲突，**不建议在本架构实现**。

## 3. 安全性对比

威胁模型：S 为诚实但好奇（honest-but-curious），持有密文库与 V 矩阵；S 知道
监督位置与查询块/子集，不知道标签值；U 只持有 pk_M 与 PRG 种子，无法解密；
M 持有 sk_M，不持有数据库明文。

### 3.1 单查询隐私

| 方案 | S 能看到什么 | 对单个查询的猜中优势 |
|---|---|---|
| 块 PIR | block_size 个行索引的集合 | 位置级 1/block_size；**对标签值的有效猜中 ≈1/3（标签域仅 3 个 token，随机水平）** |
| RMS-PIR | 两个子集（覆盖全部分区、随机置换） | **0**（论文 Lemma 2：子集分组分布与查询索引独立，Pr(b|i)=Pr(b|i′)=τ/2） |
| S3PIR（正式方案） | 同 RMS-PIR（同一 dummy 子集技巧） | 0（单查询不可区分） |

因此**单查询隐私 RMS-PIR/S3PIR 严格优于块 PIR**：块 PIR 仍有 1/64 的猜中概率，
而论文方案在单查询下是信息论不可区分的（给定 PRF 伪随机性）。

### 3.2 多查询隐私（重点）

#### 3.2.1 块 PIR：跨查询频率泄露（实测可恢复）

块 PIR 的每个查询块都会**重复包含真实行**：真实标签 y 在每个真实块里出现 1 次，
而均匀采样的 dummy 行在单个块里出现概率极低（7/32000）。S 只需统计“哪些行索引
在多个查询块中出现”，就能以近乎 100% 的准确率恢复真实行。旧版模拟攻击：
**32/32 个查询块全部被频率分析恢复**（dummy 均匀、block=8）。

改进版（dummy 分布对齐真实标签边际 + block=64 + 8:2 假查询）把真实行与 dummy 行的
**每行边际分布拉齐**：真实标签域只有 {29871（空格）, 3869（Yes）, 1939（No）}，
dummy 按同样频率采样后，每个块里三者都出现约 32/16/16 次，真实行多出的 1 次
只产生 ~1-3% 的频率偏差，单块信噪比大幅下降（模拟恢复率从 100% 降至随机水平，
详见真 PIR 测试报告 §6.3）。

**但改进不消除频率泄露**：

- 只要真实查询序列不是均匀的，全局计数就会出现系统性偏差
  （`count(t) = 期望 + 真实查询 t 的次数`），S 在足够多步骤后仍可通过
  χ²/似然检验判断“哪个标签被查询得更频繁”；
- 假查询块（8:2）只是把信噪比再压低 20%，不改变泄露的**方向**；
- 若 S 进一步做**交集分析**（哪些行与哪些行总在同一块里出现），可关联出
  同一批次的标签共现模式。

结论：**块 PIR（含改进版）不满足标准（有状态）PIR 的多查询隐私定义**——服务器
可以学到查询序列的统计信息。它适合作为“单查询不可区分 + 多查询统计抗性”的
工程折中，但若安全目标要求标准 PIR 隐私，必须换用论文方案。

#### 3.2.2 RMS-PIR：hint 频率 + 交集泄露（取决于部署形态）

论文的两服务器方案在**正确部署**（offline server ≠ online server，二者非合谋）下
满足标准有状态 PIR 隐私：每个查询的两个子集是随机分组，S 无法区分真假子集，
也无法把查询与 hint 关联（online server 从没见过 hints）。论文 §3.5 证明
“查询后 hints 的分布与查询前相同”，因此**任意查询序列（含自适应）都支持**。

本项目在 **RMS-PIR v2（2026-08-19 起）** 中落实了这一职责划分：

- **offline 角色由 U 承担**：U 一次性下载 S 的密文库副本（4.2GB，Enc(-V)，
  pk_M 加密，U 无 sk 不可解密；V 为公开 lm_head 权重），在本地用 BFV worker
  计算 hint parity 与每查询的补充半区 parity；
- **online 角色由 S 承担**：S 只应答在线查询的两个子集 parity（明文聚合 +
  一次加密，与密文和位级一致），**从不见 hint 子集与半区**；
- 因此单 S 部署下 S 无可关联的 hint 状态，**单查询与多查询隐私均按论文成立**，
  不再依赖“S 不进行 hint-查询关联”这一额外假设。

代价与注意点：

- U 需要 4.2GB 本地密文库副本（一次性下载，实测 89.9s）+ 本地离线构建
  （2599 hints / 88.3s）与每查询补充计算（每 token ~160 次密文加法）；
- “密文库只在 S”的目录隔离口径变为“U 持加密副本、S 持原始库”，需如实说明；
- 若因某种原因回退到“S 既建 hints 又应答”的 v1 形态，则多查询隐私降级为
  依赖 S 不关联——当前代码已不再存在该形态。

#### 3.2.3 S3PIR：分区号明文 + 查询模式泄露

论文的单服务器方案在查询请求里用 **bit-vector + 偏移向量**编码两个子集，其中
**每个分区号 k 都是明文**（bit b_k 标记该分区属于哪个子集，偏移 r_k 标记该分区
取哪一行）。虽然 b 的分布与查询索引独立（Lemma 2），但：

- 分区级访问模式（哪些分区被访问、访问频率）完全暴露；
- 在本项目 ClinVar 场景中，标签域只有 3 个 token（29871/3869/1939），它们分别
  落在 3 个已知分区，**分区级统计几乎等价于标签级统计**；
- 论文的隐私定义只保证“服务器不知道查询索引”，不承诺隐藏查询序列的统计模式。

所以 **S3PIR 在本项目的多查询安全性与块 PIR 属于同一量级（都有统计泄露），
且实现成本（客户端需可解密/下载全库）最高**，是最不合适的选项。

### 3.3 三种方案的共同短板（与 PIR 选择无关）

1. **监督位置暴露**：S 需要知道监督位置（答案在序列中的位置）才能只给少数位置
   计算 s_share。监督位置是模板结构（答案固定跟在 “Answer:” 后），不是标签值；
   这是性能取舍（详见真 PIR 测试报告 §2）。
2. **公开输出头**：TinyLlama 的 lm_head 是公开权重，M 在推理/eval 时本就持有
   完整的 V 矩阵（通过公开权重加载），可在本地对 H_M 做 logits 计算并恢复
   Yes/No 预测。这与 TriadFT 论文的 head-confidentiality 假设不同——三种 PIR
   都无法修复这个架构层问题；本项目的隐私口径是“**U 的样本与标签不外泄给
   S/M 的消息通道**”，而非“M 无法推断预测”。

## 4. 结论与选型建议

| 方案 | 单查询隐私 | 多查询隐私 | 通信效率 | 实现复杂度 | 本架构适配性 |
|---|---|---|---|---|---|
| 块 PIR 改进版（默认） | 1/64 | 频率统计泄露（已显著压低） | 差（每步 ~336 MB） | 最低 | ✅ 直接可用 |
| RMS-PIR（备用） | 0（信息论） | 需双服务器部署才成立 | 好（每步 ~17 MB） | 高（离线+补充） | ⚠️ 需第二持库实例 |
| S3PIR（正式单服务器） | 0 | 分区模式泄露 | 中 | 高 | ❌ U 不可解密，冲突 |

**推荐路线**：

1. 当前继续使用改进版块 PIR（dummy 对齐真实分布 + block=64 + 8:2 假查询），
   文档如实记录其残余的多查询统计泄露；
2. RMS-PIR 作为备用方案保留（本仓库已实现并冒烟验证），当后续部署具备
   “offline server 与 online server 分离”条件时切换，可同时获得标准多查询
   隐私与更低的在线通信；
3. 正式 S3PIR 单服务器方案不实现——它要求客户端能处理明文数据库，
   与本项目“U 不可解密、S 唯一持库”的信任模型冲突。
