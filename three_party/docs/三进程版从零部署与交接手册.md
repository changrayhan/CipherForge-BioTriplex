# CipherForge-ClinVar 三进程版 · 从零部署与交接手册

> 版本：2026-08-19 · 适用对象：需要在另一台主机上独立部署并运行本项目的智能体/工程师。
> 范围：**只讲三进程版**（`cipherforge-three-party/`，GitHub 仓库中为
> `three_party/`）；单进程版（`clinvar-submit/` / `single_process/`）独立、互不隶属。
> 本文档与 [README.md](../README.md) 配合使用：README 讲“是什么”，本文档讲“怎么从零跑起来”。

---

## 0. 一句话总览

在 Linux（WSL 亦可）上：装好 conda 环境 → 下载 TinyLlama 快照 → 准备/复用
ClinVar QA 数据（已随仓库提供）→ 启动 M、S 两个节点服务 → 运行 U 协调者
（`coordinator/main.py`）自动完成 **Stage0（BFV 密钥 + 密文库，约 1 小时，可复用）→
Stage1（三方隐私微调）→ Stage2（adapter 导出 + AUPRC 评测）**。

```
party_s/main_s.py :9003  ──┐
party_m/main_m.py :9002  ──┼── HTTP/JSON（Base64 传输张量与密文）
coordinator/main.py (U)  ──┘   ← 训练入口，持有明文数据与标签
```

## 2. 部署步骤（一台主机从零开始）

### 2.1 拉取代码

```bash
git clone https://github.com/changrayhan/CipherForge-ClinVar.git
cd CipherForge-ClinVar/three_party        # 三进程版目录（本手册范围）
```

### 2.2 设置环境变量

```bash
export CF_MODEL_PATH=/path/to/tinyllama-snapshot   # 必填
export PYTHON=$(which python)                       # 指向 §1.2 的环境
export S_DEVICE=cpu                                 # S 节点设备（默认 cpu 最稳）
export REPO_ROOT=$(pwd)
export HF_HUB_OFFLINE=1                             # 离线加载模型快照
export PYTHONPATH=$REPO_ROOT
```

### 2.3 Stage 0：BFV 密钥 + 密文库（自动、可复用）

第一次运行 `coordinator/main.py` 时自动完成：

1. **M**：`bfv_keygen` 生成 BFV 密钥对 → 存 `party_m/keys/bfv_sk.bin`、
   `bfv_pk.bin`（sk 永不出 M 进程；已有文件则缓存命中，不重建）；
2. **S**：`build_enc_db` 加载 lm_head（V 矩阵，32000×2048）→ 逐行 BFV 加密为
   `Enc(-V_y)` → 写 `party_s/db/bfv_ct_db_n32000_d2048_p4096.bin`
   （约 4.2GB，**首次约 1 小时**，之后复用）。

> 三主机部署时：M 生成密钥 → 只把 `bfv_pk.bin` 分发给 S → S 在自己主机构建密文库；
> sk 只在 M 主机。

### 2.4 Stage 1：三进程微调（一键）

```bash
bash scripts/run_full.sh --max_train_steps 1875 --batch_size 16 --log_freq 10
```

`run_full.sh` 内部等价于：

```bash
python -u -s party_s/main_s.py --port 9003 --db_dir party_s/db --device cpu &   # S 节点
python -u -s party_m/main_m.py --port 9002 --keys_dir party_m/keys &           # M 节点
sleep 3
python -u -s coordinator/main.py --config coordinator/three_party_config.json "$@"
```

### 2.5 Stage 2：导出 + 评测（训练结束后自动执行，也可单独跑）

```bash
bash scripts/run_full.sh --skip_train    # 加载 last_checkpoint → 导出 adapter → 评测
```

结果写 `coordinator/logs/clinvar_auprc.json`；adapter 在
`coordinator/adapter/`（LoRA 权重 + `adapter_config.json`）。

### 2.6 冒烟验证（新环境先跑这个）

```bash
bash scripts/run_smoke.sh    # 40 步 + 小验证 + adapter 导出（约 5-6 分钟）
```

验收标准：日志无 PIR/密文错误、`loss_ce` 有正常波动、`smoke_rc=0`。

| `poly_degree` / `plain_bits` / `scale` | 4096 / 30 / 10000 | BFV 参数（与密文库绑定，勿改） |

| `pir_block_size` | 64 | 块 PIR 块大小（dummy+real） |

| `rms_partition_size` / `rms_lam` / `rms_min_coverage` / `rms_offline_chunk` | 200 / 16 / 20 / 64 | RMS-PIR 分区/池/覆盖率/分块参数 |
| `rms_db_dir` | `${REPO_ROOT}/party_u/db` | U 本地密文库副本（RMS v2 自动下载并缓存） |
| `rms_db_download_chunk_mb` | 32 | 密文库分块下载大小 |
| `dp_enable` / `dp_alpha` / `dp_eta0` | true / 0.15 / 900.0 | 差分隐私开关 / 相对噪声比 / 显式噪声强度 |
| `dp_answer_beta` / `dp_num_classes` | 0.5 / 2 | 答案位置噪声放大倍数 / ClinVar 二分类类数 |
| `dp_calibration_steps` / `dp_calibration_mode` | 1 / false | EMA 校准步数 / 是否仅校准不加噪（当前默认显式 η0） |
| `dp_clip_value` | null | 可选噪声/输出 L∞ 裁剪 |
| `http_timeout_s` | 600 | 大载荷 HTTP 超时（块 64 时必须足够大） |
| `u_layers` / `m_layers` | 11 / 11 | U/M 各持 11 层（22 层模型） |

| `batch_size` | 16 | 每步样本数（16 → 每步 32 个监督 token） |

| `val_metric` / `patience` | `val_ce_loss` / 999 | 验证早停（默认不早停） |
| `N_CRYPTO_U/M/S_WORKERS` | 1 / 1 / 1 | SEAL worker 数；**13GB 内存机保持 1** |
| `CHUNK_TOKENS` | 128 | 每步 token 上限（batch=16 时实际 32） |
| `seed` | 42 | 数据 shuffle 与训练种子 |

## 5. 隐私与安全要点（运行前必读）

1. **标签值永不出 U**：U 只发“监督位置 + 查询块索引集合”；S 只知道监督位置
   （答案在序列的哪两个位置），不知道 Yes/No 取值；M 只收密文与份额。
2. **块 PIR v2 是默认**：dummy 按标签边际采样（coordinator 自动从训练集计算）、
   block=64、8:2 假查询；其多查询频率泄露已压低到随机水平（见
   `docs/真PIR隐私保护测试报告.md` §6.3），但**不满足标准 PIR 多查询隐私**。
3. **RMS-PIR 是备用**（`pir_mode: rms`，v2）：U 持密文库加密副本当 offline 端，
   S 持明文 V 只应答在线子集；S 从不见 hint 状态，多查询隐私按论文成立。
   注意：U 端需一次性下载 4.2GB 密文库到 `party_u/db/`（pk_M 加密、U 不可解密）。
4. **差分隐私默认开启**：U 端在 `H_U` 出域前注入多元拉普拉斯噪声
   （`shared/core/dchi_privacy.py`），`dp_eta0` 显式校准；关闭可设
   `dp_enable: false`。
4. 真实跨主机部署必须加 **TLS**（PRG 种子、pk、H_U/H_M 都在网上传）。

## 6. 多主机（三台 RTX 4060）部署

1. 三台装同一 conda 环境与同一份代码；
2. M 机先跑一次 `bfv_keygen`（或直接复用仓库 `party_m/keys/` 中已生成的密钥）；
3. 把 `bfv_pk.bin` 拷贝到 S 机，S 机运行 `party_s/main_s.py --host <S_IP> --port 9003
   --model_path ... --device cpu`，首次自动构建 4.2GB 密文库；
4. M 机运行 `party_m/main_m.py --host <M_IP> --port 9002 --model_path ...`；
5. U 机修改 `three_party_config.json` 的 `nodes.M/S` 为对应 IP，运行
   `coordinator/main.py`；
6. 千兆有线网下预计步时 1.3-1.8s；WiFi 2-3s（仅演示用）。

> 防火墙需放行 9002/9003 与协调者出站；`prg_seed` 由 U 生成后发给 S，
> 公网环境必须走 TLS（当前 HTTP 仅限本机/受信内网）。

## 7. 常见问题排查

| 现象 | 原因与处理 |
|---|---|
| `CF_MODEL_PATH must be set` | 未导出模型路径；见 §2.2 |
| S 构建密文库耗时 1 小时 | 正常（32000 行 BFV 加密）；完成后自动复用 |
| `fetch_rows failed` / 超时 | `http_timeout_s` 太小；块 64 时建议 ≥600 |
| 训练 loss 尖峰/NaN | 检查 `poly_degree/plain_bits/scale` 是否与密文库一致；PRG 掩码边界已内置修复 |
| 内存不足 | `N_CRYPTO_*_WORKERS` 全部保持 1；S 用 `--device cpu`；关闭其他 CUDA 进程 |
| LoRA 梯度恒为 None | M 侧 `H_U.requires_grad_(True)` 逻辑被误删（`main_m.py act_trunk_forward`） |
| RMS 报 `no hint containing label` | `rms_min_coverage` 太小或 `rms_lam` 太小；默认 20/16 不应出现 |
| GPU 无反应 | U/M 的 CUDA 上下文在 WSL/主机间不共享；确认 `torch.cuda.is_available()` 为 True |
| 评测 accuracy@0.5 偏低 | 该指标对概率校准敏感，项目以 AUPRC/AUC/per-gene AUPRC 为准 |

## 8. 参考结果（验收基准）

5k/类数据、lr=2e-4、LoRA r=8/α=16、3 epochs、batch=16：

| 指标 | 明文 LoRA 基线 | CipherForge 三进程版 |
|---|---:|---:|
| AUPRC | 0.7922 | 0.7976（单进程版 0.8033） |
| AUC | 0.7936 | 0.7887 |

新部署跑通后，AUPRC 落在 ±0.01 内即为正常（浮点量化噪声范围）。
